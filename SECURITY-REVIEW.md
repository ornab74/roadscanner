# Roadscanner Cloudflare security review — 2026-11-12

This targeted review covers the deployed Cloudflare Worker architecture. It is not a completed exhaustive repository audit or a guarantee that vulnerabilities are absent. The security plugin's shared scan references were unavailable, so its canonical scan/report workflow could not be completed. Findings below come from direct source inspection, focused tests, dependency checks, and Cloudflare API configuration reads.

## Changes applied

- Removed global loading of vendored jQuery 3.5.1 and Bootstrap 4.5.2 JavaScript from generated Cloudflare pages. Active pages used those plugins only for three public mobile menus; a small self-hosted `nav-collapse.mjs` module now toggles known navigation elements using class/ARIA state. Bootstrap CSS remains for layout, and the legacy repository assets remain available for the separate legacy app. This is attack-surface reduction, not a claim of an exploitable library vulnerability. Browser checks covered Home/Login/Register at mobile and desktop widths, click and keyboard toggling, and absence of legacy script tags. SRI checks pass against the rebuilt asset bytes.

- Migration `0011_resource_limits.sql` adds database insert triggers for 20 active garage vehicles, 20 active non-browser API keys, and 10 passkeys per account. Application prechecks remain for fast responses; database triggers enforce the same caps atomically against concurrent insertions. Expired/revoked API keys and browser pseudo-keys do not consume the active API-key cap. Deleted vehicles and removed passkeys release capacity. Existing records are preserved. Quota trigger failures return sanitized 409 errors. Tests exercise direct inserts beyond each cap, released capacity, another account, and a stale application count returning 19 when 20 vehicles already exist.

- Scene scans now share an account-level limit of 20 new scans per minute across all API keys and browser scans, in addition to the existing 20-attempt per-key limit. Previously multiple keys could multiply one account's inference allowance. The account check occurs before credit reservation/provider work and after stored replay lookup. Regression coverage seeds an exhausted account budget, switches between two valid keys, verifies 429 with Retry-After and no extra charge/provider work, and verifies stored replay remains usable. This is a request quota, not a dollar spending cap.

- Added a free custom WAF rule scoped to `ride.qroadscan.com`, reference `qrs_block_private_file_probes_v1`: block leading `.env` and `.git` probes, `/.DS_Store`, and TRACE/TRACK/CONNECT methods. Existing two custom rules were preserved; three custom rules are now configured. These paths were already outside application routes; edge blocking reduces unnecessary Worker traffic and provides protection against future accidental exposure. Live probes returned edge 403 responses without the Worker's request identifier.
- Added a free cache rule scoped to the same hostname, reference `qrs_private_cache_bypass_v1`, setting cache eligibility false for `/api/`, `/auth/`, `/settings/`, `/billing/`, `/dashboard`, `/admin` and `/aircraft` surfaces. Application no-store headers remain in place. Live API/config/CSRF/session checks confirmed uncached responses, authentication and no-store behavior; public Docs continued to serve normally from cache. This is the only cache rule currently configured. To roll back either addition, delete only the rule with its matching reference from the corresponding zone ruleset; preserve other rules.
- Cloudflare URL normalization is already enabled for incoming requests. No paid product, plan upgrade, Turnstile challenge, or extra API rate-limit rule was enabled. The zone's existing free rate-limit rule covers older endpoints and was preserved; current endpoints retain the application's own rate limits.
- Follow-up registrar API inspection confirmed `qroadscan.com` uses Cloudflare Registrar. Cloudflare's DNSSEC documentation states it automatically adds DS records for its registrar domains. Enabled free DNSSEC through the zone API: status is currently `pending`, algorithm 13, key tag 2371. Public Google DNS queries returned DNSKEY and RRSIG records, but no parent DS and no authenticated-data flag yet. HTTPS health remained 200. Full chain validation is not verified until automatic registrar activation and resolver cache propagation complete. Recheck the zone DNSSEC status and public DS/A queries; expect `active`, a DS matching the zone key and validating resolver AD=true. Do not manually replace DS records or disable signing while a parent DS remains published. This is a DNS configuration change only; application code and secrets were unchanged.

- Credential lifecycle races are guarded at the database write boundary. Login session insertion and password reauthentication require the exact hash/salt snapshot that was verified. Password changes compare-and-swap that snapshot and revoke sessions in the same D1 batch. A concurrent credential replacement cannot be overwritten by a stale password-change request or followed by a stale password login issuing a new session. Regression tests inject credential replacement immediately before each affected write and verify rejection, no cookie issuance/elevation, and preservation of the replacement hash.
- Passkey session creation also rechecks the registered key at the insert boundary, including ownership, public key and the verified counter value. Removing a passkey between signature verification/counter update and session creation prevents issuance. Focused SQLite tests cover a valid zero-counter key, deletion, changed public key, mismatched owner and counter. These tests exercise session issuance; they do not simulate a physical authenticator ceremony.

- Login previously limited attempts only by connecting IP. Distributed clients could target one password without sharing that limit. Login now additionally permits at most 30 attempts per normalized email per five-minute fixed window. Email rate keys use HMAC rather than plaintext. This applies equally to existing and nonexistent accounts. Existing per-IP protection remains. An attacker can temporarily exhaust this account limit; passkey login remains separate.
- Enabled execution of Cloudflare's free managed WAF ruleset for `ride.qroadscan.com` only. Existing custom and rate-limit rules were preserved. No paid product was enabled.

## Verified evidence

- Follow-up API/data-access review found no additional confirmed bypass in the inspected garage, image, report pagination, operation status, aviation and browser/admin scope boundaries. Added a denial matrix using an account-only key across eleven feature endpoints and three browser-only endpoints; requests are rejected before scanner calls or credit consumption. Existing tests cover owner-bound cursors/report retrieval and scoped marker output. Explicit full-scope legacy defaults remain documented compatibility behavior; the Settings UI submits an explicit preset.
- Follow-up verification: all 79 existing Cloudflare tests passed, then all seven API-contract tests passed with the added denial matrix. The production dependency audit again returned zero known advisories. Reviewed imagery download origin/path checks and redirect handling, image dimension/byte limits, and constrained SVG interpolation; no new confirmed vulnerability was identified in those inspected paths. This result does not expand coverage to all legacy deployment components or certify model/navigation output.

- Focused Worker/security/account tests: 23 passed, including rotating-IP attempts, case/whitespace email normalization, unrelated account login, CSRF rejection, administrator authorization and elevation, expiring/revoked API keys, report ownership, billing reservation/refund behavior, and encrypted report storage.
- `npm audit --omit=dev --json` in `cloudflare`: no known production dependency advisories at review time.
- Source confirms HttpOnly/Secure/SameSite session cookies, signed browser CSRF tokens, strict CSP, scoped API authentication, private encrypted R2 image retrieval with no-store responses, bounded request/provider bodies, and a scanner container with outbound internet disabled.
- Cloudflare settings already enable Always Use HTTPS, strict origin TLS, TLS 1.3 minimum, Browser Integrity Check, and Bot Fight Mode. 0-RTT is disabled. Managed DDoS protection is provided by Cloudflare. R2 images use the Worker binding rather than public image bucket URLs.

## Remaining limits and follow-up

- The deployment environment currently uses an account-wide Global API Key. Replace it with a narrowly scoped deployment token when practical; this review did not revoke or rotate credentials and interrupt deployment access.
- Disabled the production Worker development hostname (`workers_dev: false`); preview URLs remain disabled. Production traffic uses the custom domain and its zone WAF controls. Local test origins remain independent of the deployed routing configuration.
- Password storage now uses the versioned `qrs-pbkdf2-sha256-hmac-v1$100000$` format: salted PBKDF2-SHA256 at the Workers-supported 100,000 iterations, followed by HMAC-SHA256 under a dedicated Worker secret, bound to the salt and derived hash. Existing unversioned hashes upgrade on successful password login with a new random salt and compare-and-swap protection. Registration and password changes write the new format; reauthentication accepts both formats. The pepper is independent of Cloudflare deployment credentials and API-key lookup keys. Loss or rotation of the pepper requires a password-reset/recovery plan: do not replace it casually. Database-only compromise no longer permits offline verification of new hashes without that secret. This does not increase PBKDF2's iteration count or protect an attacker who obtains both database and Worker secrets.
- No claim is made of full legacy Flask, installer, supply-chain, Cloudflare-account membership, or historical-secret exposure coverage. Production user credentials were not used for attack testing. Provider model calls were mocked in the focused suite.
- Anonymous homepage model calls remain subject to existing per-IP and global application limits, rather than a new interactive challenge. API clients are not required to solve browser challenges by the added WAF execution rule itself; managed rule matches may still block malicious requests.

The next security review should complete repository-wide source coverage and assess account-scoped deployment credentials, password-hash migration, and canonical-host enforcement.
